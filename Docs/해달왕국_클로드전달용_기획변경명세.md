# 해달 왕국 — 클로드 전달용 기획 변경 명세

작성일: 2026-09-22  
문서 성격: 기존 상세 기획서에 대한 변경·보완 문서

## 1. 문서 적용 기준

이 문서는 기존 기획서를 읽은 클로드가 제기한 여섯 가지 질문에 답하고, 이후 사용자가 구체화한 게임 방향을 전달하기 위해 작성했다.

- **확정**: 사용자가 직접 설명하거나 선택한 사항. 기존 기획서와 충돌하면 이 문서의 확정 사항을 우선한다.
- **제안**: 구현을 단순하게 하거나 모호함을 줄이기 위한 권장안. 사용자가 확정한 것으로 취급하지 않는다.
- **미정**: 아직 선택되지 않은 규칙. 관련 기능을 구현하기 전에 선택하거나, 임시 구현이라면 가정을 명시한다.

기존 기획서 전체가 폐기되는 것은 아니다. 다만 아래 변화와 연결된 생산 수치, 목표, 해금 조건, 세이브 구조, 개발 일정은 다시 검토해야 한다. 이전 숫자를 그대로 유지한 채 새 기능만 추가하지 않는다.

기본 전략은 유지한다. 작은 플레이 가능 버전을 먼저 만들고, 반응을 확인한 후 추가 개발한다. 요리는 별도 프로젝트인 ‘해달 식당’과 중복되므로 이번 게임에서 제외한다.

## 2. 변경된 게임의 중심 구조

**밭과 물가를 확장하고 해달을 배치해 생산하며, 광장에서는 물건을 가지고 노는 해달들의 모습을 구경하는 게임.**

핵심 구성은 다음과 같다.

1. 생산: 밭에서 작물을 재배하고, 초기 낚시터에서는 해달이 직접 수영하며 채집한다.
2. 확장: 재화를 모으고 해달 해금 조건을 충족해 작업 공간을 늘린다.
3. 해달: 사용할 수 있는 해달도 점차 늘리고 작업 시설에 배치한다.
4. 관찰: 광장에 물건을 놓고 해달들이 돌아다니거나 물건과 상호작용하는 모습을 본다.

‘생산으로 얻은 재화를 공간·해달·놀거리에 사용한다’는 연결을 목표로 한다. 다만 해달의 구체적인 획득 방식과 각 가격은 아직 미정이다.

## 3. 구역 이동과 화면 구성

### 3.1 확정 사항

밭, 낚시터, 광장을 구분한다. 맵 화살표 또는 표지판 UI에서 목적지를 누르면 해당 구역으로 이동하고 현재 위치를 표시한다.

| 구역 | 위치 표시 | 화면의 중심 |
|---|---|---|
| 밭 | 현재 위치: 밭 | 개간된 밭, 작업 해달, 옆의 잠긴 밭 |
| 낚시터 | 현재 위치: 낚시터 | 수영·채집하는 해달, 확장 가능한 작업 공간 |
| 광장 | 현재 위치: 광장 | 돌아다니는 해달, 플레이어가 배치한 물건 |

첨부했던 ‘해달 왕국’ 이미지는 따뜻한 마을 분위기, 나무 표지판, 해달 중심 화면 구성의 참고다. 이미지 속 요리 시설, 의뢰, 유료 재화, 보물상자 등이 모두 구현 요구사항이 되는 것은 아니다.

### 3.2 제안 사항

- 다른 구역을 보는 동안에도 배치된 해달의 생산은 계속된다.
- 화면 전환과 생산 상태를 분리한다. 구역 오브젝트의 비활성화가 생산 중단으로 이어지면 안 된다.
- 별도 유니티 Scene을 사용할지, 한 Scene 안에서 구역을 전환할지는 구현 선택이다. 구역 분리가 곧 Scene 분리를 의미하지는 않는다.
- ‘M1 밭’, ‘M1 낚시터’라는 표현은 기존 문서의 개발 단계 M1과 혼동될 수 있다. 시설은 ‘밭 1번’, ‘물가 1번’처럼 부르고 개발 단계와 구분한다.

## 4. 시설 확장과 해달 배치

### 4.1 확정 사항

- 밭과 낚시터 모두 확장 가능해야 한다.
- 시설에 배치할 수 있는 해달도 늘릴 수 있어야 한다.
- 첫 밭은 처음부터 개간되어 있다.
- 첫 밭 옆에는 잠긴 밭이 보인다.
- 재화가 충분하면 추가 밭을 개간할 수 있다. 단, 필요한 일꾼 해달도 해금되어 있어야 한다.
- 기존의 ‘농부 해달 한 마리 고정, 밭이 늘어도 해달 개체는 추가하지 않음’ 규칙은 폐기한다.

확장 가능한 구조와 초기 콘텐츠 수량은 구분한다. 데이터로 시설과 해달을 추가할 수 있게 하되, 처음부터 많은 개체와 구역을 제작할 필요는 없다. 기존의 밭 최대 3개·낚시터 1개를 최종적인 시스템 한도로 고정하지 않는다.

### 4.2 구분해서 관리할 상태

| 상태 | 의미 |
|---|---|
| 해달 해금 | 해당 해달을 사용할 자격을 얻은 상태 |
| 시설 개방 | 밭 개간 또는 물가 작업 공간 개방이 끝난 상태 |
| 해달 배치 | 특정 해달을 특정 작업 공간에 지정한 상태 |
| 생산 준비 | 배치, 모종 선택 등 해당 시설의 생산 조건이 충족된 상태 |

### 4.3 권장 기본안 — 사용자 확정 전

- 작업 공간 1개당 해달 1마리를 배치한다.
- 해달 1마리는 동시에 작업 공간 1개에만 배치할 수 있다.
- 첫 밭에는 시작 해달을 기본 배치한다.
- 개간은 ‘재화 + 필요한 해달 해금’을 검사한다.
- 생산은 ‘실제 해달 배치 + 해당 작업의 준비 조건’을 검사한다.

**아직 구분이 필요한 부분:** 개간 시 해달이 해금되어 있기만 하면 되는지, 아니면 미배치 해달이 있어야 하는지는 미정이다. 모든 밭에 공통 일꾼을 사용할지, 특정 밭에 특정 해달이 필요한지도 미정이다.

재배치 기능을 넣는다면 작업 중 해달을 뺐을 때 진행률을 일시 정지할지, 현재 회차를 끝내고 이동할지도 정해야 한다. 보상 중복이나 진행 초기화 문제가 생길 수 있으므로 임의로 구현하지 않는다.

## 5. 밭과 모종 선택

### 5.1 확정 사항

개방된 밭에서는 플레이어가 보유한 모종을 직접 선택할 수 있다. 새 밭에 작물을 임의로 지정하지 않는다.

### 5.2 Idle 상태의 권장 처리

아래를 첫 구현의 제안 규칙으로 둔다.

1. 밭이 개방되면 모종을 선택할 수 있다.
2. 해달 배치 전에도 모종 선택 자체는 허용한다.
3. 해달이 배치되어 있고 유효한 모종도 선택되어 있다면 즉시 생산을 시작한다.
4. 둘 중 하나가 없으면 대기하며, 부족한 조건을 UI에 표시한다.
5. 별도의 ‘생산 시작’ 버튼은 두지 않는다.

이렇게 하면 ‘최초 Idle 상태에서 작물을 고르면 즉시 시작하는가’에 대해 **생산 조건이 모두 충족되면 즉시 시작한다**고 명확히 답할 수 있다.

### 5.3 모종의 성격 — 미정

| 선택지 | 의미 | 추가로 필요한 설계 |
|---|---|---|
| 영구 해금형 | 한 번 얻은 모종의 작물을 계속 재배 | 모종 획득 조건과 작물 선택 |
| 소모형 | 심을 때마다 모종 수량 차감 | 구매·재고·부족 처리·자동 재파종 |

초기 버전에는 영구 해금형을 제안한다. 사용자가 ‘보유한 모종’이라고 표현했지만 소모 여부까지 확정한 것은 아니다.

생산 중 작물 변경, 저장소 만석, 자동 반복 생산은 기존 규칙을 출발점으로 검토할 수 있다. 그러나 모종을 소모형으로 선택하면 모종 차감 시점과 오프라인 재파종까지 다시 설계해야 한다.

## 6. 초기 낚시터는 수영 채집으로 구현

### 6.1 확정 사항

- 처음부터 낚싯대나 장비를 사용하지 않는다.
- 해달이 직접 수영하고 잠수하면서 조개 등을 채취한다.
- 낚시터도 확장하고 배치 해달을 늘릴 수 있어야 한다.

초기 작업의 핵심 연출은 ‘물에 들어감 → 수영·잠수 → 채집물을 가져옴’이다. 세부 동작 순서와 길이는 아트 제작에 맞춰 정한다.

### 6.2 기존 기획에서 교체할 부분

- ‘낚시터 1개 고정’을 확장 가능한 작업 공간 구조로 변경한다.
- ‘낚싯대 드리우기·찌 흔들림’을 초기 수영·채집 연출로 교체한다.
- 기존 물고기 5종과 확률표를 초기 채집물 목록으로 그대로 사용하지 않는다.
- 초기 채집물 종류, 수량, 생산 주기, 판매 가격, 결과의 확률 여부는 새로 정한다.

장비 낚시를 후속 단계로 도입할 수는 있지만 이번에 확정된 구현 요구사항은 아니다.

기존 문서의 재화 이름은 ‘조개’였는데, 실제 채집물도 조개가 되면 혼동될 수 있다. **재화는 코인, 채집물은 조개로 구분하는 안을 제안**하며 명칭 변경 자체는 아직 확정하지 않는다.

## 7. 광장과 해달의 놀이

### 7.1 확정 사항

플레이어가 광장에 물건을 배치하면 해달들이 돌아다니다 물건을 가지고 놀거나 상호작용한다. 네코 아츠메처럼 해달의 귀여운 행동을 관찰하는 재미를 지향한다.

광장은 단순한 장식 배경이 아니다. 배치된 물건이 해달의 행동과 연결되어야 한다. 다만 방문 확률, 먹이, 선물, 사진첩 등 다른 게임의 시스템 전체를 도입하라는 뜻은 아니다.

### 7.2 최소 행동 흐름 제안

`대기 → 이동 → 사용 가능한 물건 선택 → 접근 → 놀이/휴식 → 사용 종료 → 다음 행동`

물건마다 최소한 다음 정보를 정의한다.

| 정보 | 용도 |
|---|---|
| 물건 종류 ID | 외형과 행동 정의 연결 |
| 배치 개체 ID | 같은 물건 여러 개를 구분 |
| 배치 위치 | 저장 및 복원 |
| 접근·상호작용 위치 | 해달이 다가가서 멈출 지점 |
| 상호작용 종류 | 앉기, 눕기, 공놀이 등 동작 연결 |
| 동시 이용 가능 수 | 같은 자리에 여러 해달이 겹쳐 사용하지 않도록 제한 |

### 7.3 범위를 작게 유지하는 제안

- 첫 테스트는 놀거리 2~3종으로 상호작용 재미를 확인한다.
- 지정된 배치 자리를 먼저 사용하는 안과 자유 배치 안을 구분한다. 자유 배치·회전·충돌 검사는 아직 확정되지 않았다.
- 단순한 고정 경로나 이동 지점으로 해결할 수 있다면 복잡한 길찾기를 먼저 만들지 않는다.
- 광장이 화면에 없을 때 놀이 애니메이션까지 계속 시뮬레이션할 필요는 없다. 생산과 광장 연출의 시간 처리를 분리한다.

### 7.4 광장에 등장할 해달 — 미정

미배치 해달이 광장에서 노는 안을 제안한다. 다만 모든 해달을 생산에 배치했을 때 광장이 비는 문제가 있다.

다음 중 어떤 방식을 사용할지는 아직 결정되지 않았다.

- 미배치 해달만 등장.
- 작업 해달과 별도로 방문 해달 등장.
- 작업과 휴식을 오가는 규칙 도입.

작업 중인 동일 해달을 광장에도 동시에 표시하는 방식을 임의로 확정하지 않는다. 휴식으로 생산이 중단되거나 감소하는 규칙도 아직 없다.

## 8. 저장 방식: JsonUtility 확정

### 8.1 결정

- JsonUtility를 사용한다.
- 세이브 데이터에 Dictionary를 사용하지 않는다.
- 직렬화 가능한 클래스와 List 기반으로 저장한다.
- Newtonsoft.Json 도입을 기본 전제로 삼지 않는다.

현재 기획에서 Dictionary를 저장 구조로 사용해야만 하는 요구사항은 없다. 고유 ID와 리스트 항목으로 시설, 해달, 가방, 배치 정보를 표현할 수 있다.

### 8.2 저장 구조 예시

| 데이터 | 구조 예시 |
|---|---|
| 보유 생산물 | `List<ItemStack>`: itemId, quantity |
| 영구 해금 모종 | `List<string>`: 모종 ID |
| 소모형 모종을 선택할 경우 | `List<SeedStack>`: seedId, quantity |
| 해달 | `List<OtterSaveData>`: 개체 ID, 종류 ID, 해금 상태 |
| 시설 | `List<FacilitySaveData>`: 시설 ID, 개방 상태, 작업자 ID, 생산 진행 |
| 광장 배치물 | `List<PlacedObjectSaveData>`: 배치 개체 ID, 물건 종류 ID, 위치 |
| 도감 | `List<string>`: 발견한 항목 ID |

세이브 최상위는 버전 필드와 각 리스트를 가진 `SaveData` 클래스 형태로 감싼다. 표는 구조 예시이며 최종 필드 명세는 아니다.

관계는 리스트 인덱스 대신 안정적인 ID로 저장한다. 항목 순서가 바뀌어도 작업자와 시설의 연결이 유지되어야 한다. 같은 외형의 해달이 여러 마리 등장할 가능성에 대비해 ‘해달 종류 ID’와 ‘해달 개체 ID’를 구분한다.

배치 관계는 한쪽을 기준으로 저장한다. 예를 들어 시설의 workerId를 기준으로 삼고 해달의 작업 시설은 로드 후 계산한다. 양쪽에 중복 저장한다면 불일치 검증이 필요하다.

### 8.3 실행 중 Dictionary 사용 가능성

저장 자료구조와 실행 중 조회 자료구조는 별개다. 다음처럼 ID 조회가 잦아지면 Dictionary가 유용할 수 있다.

- workerId로 해달 개체 찾기.
- facilityId로 시설 상태 찾기.
- itemId로 아이템 정의 찾기.

필요할 경우 로드한 리스트에서 조회용 Dictionary를 구성하고, 저장은 계속 리스트로 수행할 수 있다. 초기 규모에서는 리스트 검색으로 시작해도 된다. **사용자가 확정한 것은 ‘Dictionary 없는 JsonUtility 세이브’이며, 코드 전체의 Dictionary 사용 금지는 아니다.**

로드 시 중복 ID, 존재하지 않는 작업자 ID, 한 해달의 중복 배치 등을 검증한다. 세이브 버전, 백업, 수령·구매의 중복 처리 방지 요구는 유지한다.

참고: 유니티 공식 JsonUtility 문서의 직렬화 클래스·리스트 예시  
https://docs.unity.com/en-us/engine/6000.6/script-reference/unityengine/jsonutility

## 9. 입력·코드·아트 결정

| 항목 | 확정된 방향 | 클로드가 할 일 |
|---|---|---|
| 입력 | 새 Input System 사용 | 실제 프로젝트 버전·패키지·UI 입력 연결 확인 후 설정 |
| 해달 식당 코드 | 다른 레포이며 이번 작업과 관계없음 | 재사용 코드 제공을 기다리지 말고 별도 프로젝트로 구현 |
| 해달 이미지 | 이후 ChatGPT에서 캐릭터별 이미지 제작 예정 | 임시 스프라이트로 개발하고 교체 가능한 연결 구조 유지 |
| 참고 이미지 | 해달 왕국의 분위기·UI 참고 | 이미지 속 모든 기능을 구현 범위로 확대하지 않음 |

새 Input System 사용 방향은 확정이지만 프로젝트의 설치 상태를 확인했다는 의미는 아니다. 레거시 입력을 기본으로 구현하지 않는다.

캐릭터 아트 제작은 앞으로 진행할 작업이다. 완성 에셋이 이미 제공되었다고 가정하지 않으며, 이번 문서 작성 요청에는 이미지 생성이 포함되지 않는다.

## 10. 클로드가 제기한 여섯 가지 질문에 대한 답변

| 질문 | 답변 |
|---|---|
| 1. 농부 1마리로 여러 밭을 어떻게 표현하는가? | 기존 농부 1마리 고정 규칙을 폐기한다. 시설 확장과 함께 배치 가능한 해달도 늘린다. 시설당 1마리는 제안값이다. |
| 2. Idle에서 작물을 처음 선택하면 바로 생산하는가? | 개방 즉시 보유 모종을 선택할 수 있다. 해달 배치와 모종 선택이 모두 충족되면 즉시 시작하는 안을 제안한다. |
| 3. 어떤 저장 직렬화기를 사용하는가? | JsonUtility 확정. 세이브는 클래스·리스트 구조로 작성한다. |
| 4. 어떤 입력 시스템을 사용하는가? | 새 Input System 확정. 실제 패키지 상태는 프로젝트에서 확인한다. |
| 5. 해달 식당의 어떤 코드를 재사용하는가? | 해당 레포와 관계없는 별도 작업이다. 재사용을 전제로 하지 않는다. |
| 6. 캐릭터 레퍼런스가 필요한가? | 해달 이미지는 이후 제작한다. 임시 아트로 기능 구현 가능하며 최종 아트와 교체할 수 있게 한다. |

## 11. 기존 기획서에서 수정해야 할 부분

| 기존 내용 | 변경 방향 |
|---|---|
| 모든 생산 시설이 있는 고정 마을 화면 | 밭·낚시터·광장 구역과 화살표 이동 |
| 농부 1마리가 전체 밭을 대표 | 여러 해달 해금·배치 구조 |
| 밭 개방은 재화·시설 레벨 중심 | 일꾼 해달 해금 조건 추가 |
| 낚시터 1개 고정 | 확장 가능한 물가 작업 공간 |
| 시작부터 장비 낚시 | 초기에는 수영·잠수 채집 |
| 최초 물고기 5종 확률표 | 초기 채집물 구성과 생산 규칙 재설계 |
| 장식은 고정 위치 외형 변화 | 광장 물건 배치와 해달 상호작용 |
| 입력·직렬화 방식 선택 유보 | 새 Input System·JsonUtility 확정 |
| Dictionary 모양의 세이브 예시 | ID를 가진 항목 리스트로 변경 |
| 해달 식당 코드 재사용 검토 | 재사용 전제 제거 |
| 참고 이미지 미제공이 아트 확정 제약 | 임시 아트로 기능 진행, 이후 제작 이미지 연결 |

기존의 첫 강화→낚시 개방 튜토리얼, 밭·어종 수량, 시설 최대 레벨, 가격과 일정은 새 해금·배치 흐름과 맞는지 재검토한다. 이번 문서가 기존 수치의 유효성을 보장하지 않는다.

## 13. 클로드에게 요청하는 후속 작업

1. 위 확정 사항을 기준으로 기존 기획과 코드의 충돌 지점을 정리한다.
2. 제안과 미정을 사용자 확정으로 바꾸어 기록하지 않는다.
3. 공통 시설 상태, 해달 배치 관계, 구역 전환, 리스트 기반 세이브의 최소 설계를 제시한다.
4. 실제 레포가 제공되었다면 유니티 버전, Input System 패키지와 기존 구조를 확인한다.
5. 첫 검증 범위는 ‘첫 밭 + 해달 + 모종 선택 + 생산 + 저장’으로 작게 유지하고, 이후 두 번째 밭으로 배치·확장을 검증하는 순서를 제안한다.
6. 초기 수영 채집과 광장 상호작용을 추가할 때는 각각 최소 한 가지 행동으로 먼저 검증한다.
7. 구현을 막는 미정 사항만 모아서 확인하고, 독립적으로 진행 가능한 기반 작업은 계속한다.

목표는 확장 가능한 구조를 갖추면서도 작은 버전으로 **생산·확장·해달 관찰의 재미**를 확인하는 것이다.
