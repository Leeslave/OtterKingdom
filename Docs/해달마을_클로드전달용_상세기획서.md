# 해달 마을 — 클로드 전달용 상세 기획서

문서 버전: 0.1 / 작성일: 2026-09-22  
목적: 유니티로 작은 플레이 가능 버전을 만들고, 실제 반응을 확인한 후 추가 개발 여부를 결정한다.

> **문서의 확정 수준**  
> 기존 대화에서 확인된 방향은 ① 해달 캐릭터 IP를 활용한 게임 ② 농사와 낚시부터 개발 ③ 요리는 별도 프로젝트인 ‘해달 식당’과 중복되므로 제외 ④ 처음부터 전체 게임을 완성하지 않고 반응을 보고 추가 개발한다는 것이다.  
> 이전 개발 계획의 상세 답변은 이번 작성 시 확인하지 못했다. 아래 게임명, 플랫폼, 콘텐츠 수량, 시간, 가격, 개발 일정, 판단 기준은 구현을 진행할 수 있도록 정한 **신규 제안값**이며 과거 합의로 간주하지 않는다. 수치는 시장 평균이나 검증된 밸런스가 아니다.

## 1. 클로드에게 전달할 작업 지시

당신은 이 프로젝트의 유니티 클라이언트 개발 파트너다. 이 문서를 기준으로 농사·낚시 중심의 2D 해달 마을 게임을 단계적으로 구현한다.

1. 프로젝트 파일을 제공받았다면 먼저 유니티 버전, 패키지, 입력 방식, UI 구성, 저장 구조와 기존 코드를 확인한다. 버전 업그레이드나 전면 재작성부터 시작하지 않는다.
2. 프로젝트 파일이 없다면 접근했다고 말하지 않는다. 아래 설계를 기준으로 필요한 스크립트, 프리팹 구성과 에디터 설정 절차를 제시한다. 기존 프로젝트 통합을 막는 정보만 질문한다.
3. 문서 전체를 읽되 **첫 작업에서는 M1의 농사 수직 슬라이스만 구현**한다. M2 이후는 M1이 검증된 후 진행한다.
4. 유저의 별도 지시가 없다면 이 문서의 제안값을 기본값으로 사용하고, 변경한 값과 이유를 남긴다. 세부 구현 선택마다 승인을 요구하지 않는다.
5. 농사·낚시·성장·저장·해달의 귀여움을 검증하는 데 필요한 기능을 먼저 만든다. 범용 프레임워크나 향후 콘텐츠를 선행 구현하지 않는다.
6. 모든 밸런스 값은 데이터로 분리한다. 임시 아트로 기능을 검증하되 외부 테스트 전에 핵심 해달 애니메이션과 수확 피드백을 넣는다.
7. 단계 완료 시 변경 파일, 에디터 연결 방법, 실제 확인한 동작, 미확인 항목, 다음 작업을 짧게 보고한다. 실행하지 않은 빌드나 테스트가 성공했다고 말하지 않는다.
8. 수익화 SDK, 계정, 서버, 상점 출시, 외부 배포는 이 문서만으로 자동 실행하지 않는다. 이 문서의 목표는 테스트할 수 있는 빌드와 판단 자료를 만드는 것이다.

## 2. 제품 목표와 검증 질문

### 2.1 한 문장 소개

**해달들이 밭과 물가에서 일하는 모습을 구경하고, 모인 생산물을 팔아 작은 마을을 키우는 편안한 방치형 게임.**

플레이어는 해달을 직접 이동시키지 않는다. 생산할 작물을 고르고, 보상을 받으며, 시설과 마을 외형을 발전시킨다. 조작의 긴장감보다 해달의 표정·행동과 마을 변화가 보상이다.

### 2.2 이번 버전에서 답할 질문

| 질문 | 확인 방법 | 판단 시 주의 |
|---|---|---|
| 해달을 보는 것 자체가 매력적인가? | 첫 화면 반응, 자유 의견, 캐릭터 관련 언급 | 이미지 호감과 게임 재방문을 구분 |
| 생산→수령→강화 흐름이 이해되는가? | 첫 수확·첫 판매·첫 강화 도달률, 관찰 | 개발자가 옆에서 설명한 결과는 별도 기록 |
| 농사와 낚시를 둘 다 이용하는가? | 기능별 시작·수령·업그레이드 | 튜토리얼 강제 사용과 자발적 사용 구분 |
| 시간이 지나 다시 들어올 이유가 있는가? | 다음 날 재방문, 오프라인 보상 수령 | 지인 의무 접속과 자발적 접속 구분 |
| 추가 콘텐츠를 원할 정도로 기본 재미가 있는가? | 목표 완료 후 행동, 구체적 요청 | “귀엽다”만으로 개발 확대하지 않음 |

### 2.3 목표 플레이 밀도

- 첫 60초 안에 첫 수확, 첫 3분 안에 판매와 강화 경험.
- 첫 10분 안에 농사와 낚시의 차이를 모두 경험.
- 첫 세션 목표는 10~15분 정도. 이후 한 번에 2~5분 확인하는 흐름을 가정.
- 초기 테스트 콘텐츠는 3~7일에 걸쳐 반응을 관찰할 분량을 목표로 한다. 플레이 기간을 강제 대기만으로 늘리지 않는다.
- 초반 콘텐츠 소진까지 걸리는 시간은 테스트로 측정한다. 본 문서의 수치만으로 일주일 분량이 확보됐다고 간주하지 않는다.

## 3. 플랫폼과 범위

### 3.1 기본 구현 가정

| 항목 | 제안 |
|---|---|
| 엔진 | 유니티 / C#; 기존 프로젝트 버전 유지 |
| 1차 타깃 | Android 세로 화면; 에디터 마우스 입력으로도 검증 |
| 화면 기준 | 1080×1920, 다양한 세로 비율과 Safe Area 대응 |
| 표현 | 2D 고정 마을 화면, 별도 자유 이동 없음 |
| 통신 | 핵심 플레이는 오프라인 가능 |
| 언어 | 한국어 우선, 문자열은 식별자로 분리 |
| 세이브 | 기기 로컬 저장, 버전 필드와 백업 지원 |

이 설정은 출시 플랫폼의 확정이 아니다. 기존 프로젝트가 가로형이거나 다른 플랫폼을 대상으로 한다면 레이아웃 결정 전에 차이를 보고한다.

### 3.2 외부 테스트용 MVP의 상한

| 분류 | 구현 수량·범위 |
|---|---|
| 마을 | 맵 1개, 고정 배치 |
| 농사 | 밭 최대 3개, 작물 3종, 농사 시설 레벨 5 |
| 낚시 | 낚시터 1개, 물고기 5종, 낚시 시설 레벨 5 |
| 해달 | 기본 외형 1종, 농부/낚시꾼 역할 소품으로 구분 |
| 성장 | 마을 단계 3개, 조개 재화 1종 |
| 꾸미기 | 고정 위치 장식 3개; 자유 배치 없음 |
| 안내 | 순차 목표 8개, 짧은 튜토리얼 |
| 수집 | 작물 3종+물고기 5종 도감 |

### 3.3 이번에 만들지 않는 기능

요리, 식당 운영, 전투, 탐험, 멀티플레이, 친구 방문, 길드, 랭킹, 가챠, 해달별 능력치, 번식, 피로도, 날씨, 계절, 복잡한 주민 AI, 자유 건설, 가구 회전, 광범위한 길찾기, 제작 재료 체인, 퀘스트 대사 시스템, 다중 통화, 출석 이벤트, 푸시 알림, 클라우드 세이브, 광고·결제 SDK.

개인 프로젝트 ‘해달 식당’의 코드를 활용하더라도 식당의 Dispatcher나 A*가 이번 고정 작업 연출에 필수인 것은 아니다. 라이선스와 의존성을 확인한 후 필요한 코드만 재사용한다.

## 4. 핵심 플레이 루프와 첫 경험

### 4.1 반복 흐름

작물 선택/낚시 시작 → 해달이 자동 생산 → 생산물 수령 → 가방의 생산물 판매 → 조개 획득 → 시설 강화·밭 개방·마을 성장 → 더 다양한 생산과 새로운 외형 변화.

생산물이 바로 재화로 변환되지는 않는다. **수령과 판매를 분리**하되 가방에서 한 번에 전체 판매할 수 있게 한다. 도감은 수령 시 영구 등록되므로 판매해도 사라지지 않는다.

### 4.2 새 게임 초기 상태

- 조개 0, 가방 비어 있음, 마을 1단계.
- 밭 1개 개방, 농사 레벨 1, 당근 선택 가능.
- 농부 해달은 밭 옆에서 대기. 낚시터는 보이지만 잠긴 상태.
- 첫 안내는 “당근을 심어 볼까?” 한 문장과 해당 밭 강조.
- 첫 튜토리얼 작물 1회만 10초 생산. 수량은 일반 생산과 동일한 5개.
- 첫 수확 전에 앱을 닫아도 튜토리얼 생산 상태와 완료 시각이 저장된다. 반복 재접속으로 단축 생산을 재지급하지 않는다.

### 4.3 순차 목표

| 순서 | 목표/완료 조건 | 보상·효과 |
|---|---|---|
| 1 | 당근 생산 시작 | 안내만; 별도 보상 없음 |
| 2 | 당근 5개 최초 수령 | 도감 당근 등록 |
| 3 | 생산물 최초 판매 | 판매 대금 외 조개 20 |
| 4 | 농사 시설 레벨 2 | 낚시터 무료 개방 |
| 5 | 물고기 최초 수령 | 조개 20 |
| 6 | 밭 2개 개방 | 조개 30 |
| 7 | 마을 2단계 달성 | 호박과 밭 3 개방 구매 자격 |
| 8 | 마을 3단계 달성 | 테스트 버전 완료 안내와 자유 플레이 |

목표 진행과 보상 지급은 분리 상태로 관리한다. 앞서 달성한 조건은 누적 기록으로 소급 인정한다. 보상 수령 버튼을 연속 눌러도 한 번만 지급한다. 마지막 안내는 “현재 준비된 마을을 모두 열었어요. 해달들과 조금 더 쉬어 가세요!” 정도로 짧게 표시한다.

## 5. 농사 시스템

### 5.1 역할

농사는 원하는 작물을 선택해 예측 가능한 보상을 얻는 콘텐츠다. 별도 씨앗 비용, 물주기, 실패, 작물 시듦은 없다. 가방의 생산물을 모두 팔거나 조개가 0이 되어도 생산을 계속할 수 있다.

### 5.2 밭 상태

`Locked → Idle → Producing → StorageFull`

- 개방한 밭은 작물 선택 후 자동 반복 생산한다.
- 생산 완료 보상은 밭 내부 저장소에 쌓인다. 가방에는 수령 시 이동한다.
- 진행 중에도 이미 쌓인 생산물은 수령할 수 있다.
- 밭마다 완료한 **6회분**까지 저장한다. 예: 당근은 5개×6회=30개.
- 6회분이 차는 순간 생산은 중단한다. 빈 슬롯이 생기면 새 생산을 처음부터 시작한다.
- 수령은 부분 수령 없이 해당 밭의 완료 보상 전체를 가져온다. 진행 중인 생산은 초기화하지 않는다.
- 작물 전환 요청은 현재 생산 종료 후 적용한다. 예약 취소/교체 가능. 완성 보상이 여러 작물로 섞여도 내부 저장은 itemId별 수량과 완료 회차 수로 관리한다.
- 저장소가 가득 찬 상태에서는 작물 변경을 즉시 선택값에 반영하되 생산은 수령 후 시작한다.
- 전환 예약이 있다면 오프라인 계산에도 정확히 한 번 반영한다.

### 5.3 작물 데이터 — 초기 제안값

| ID | 이름 | 기본 생산 시간 | 회당 수량 | 개당 판매가 | 1회 가치 | 기본 개방 조건 |
|---|---|---:|---:|---:|---:|---|
| crop_carrot | 당근 | 60초 | 5 | 2 | 10 | 시작부터 |
| crop_pumpkin | 호박 | 180초 | 4 | 8 | 32 | 마을 2단계 |
| crop_strawberry | 딸기 | 600초 | 6 | 20 | 120 | 마을 3단계 |

시설 레벨 1에서 밭 1개의 시간당 이론상 판매액은 당근 600, 호박 640, 딸기 720조개다. 저장소가 차지 않고 계속 수령한다는 가정이다. 실제 방치 수익은 저장 상한 때문에 훨씬 낮다.

작물의 핵심 차이는 수익률뿐 아니라 방치 가능한 시간이다. 당근은 자주 확인하는 플레이, 딸기는 오래 비우는 플레이에 유리하다. 작물에 현실 농사 시간은 적용하지 않는다.

### 5.4 밭 개방

| 대상 | 필요 조건 | 가격 |
|---|---|---:|
| 밭 1 | 시작 | 무료 |
| 밭 2 | 농사 레벨 2 | 100 |
| 밭 3 | 마을 2단계 | 300 |

밭은 고정 좌표에 존재한다. 잠긴 밭을 누르면 조건과 가격을 표시한다. 조건 미달과 조개 부족 메시지는 구분한다.

### 5.5 농사 연출

- 농부 해달 1마리가 밭 구역에서 심기·돌보기 동작을 반복한다. 밭별 해달 개체를 추가 생성하지 않는다.
- 밭 작물은 성장 초기/중기/완료 3단계 이미지로 표현한다.
- 수령 시 작물 아이콘이 가방 방향으로 이동하고 숫자와 작은 효과음을 표시한다.
- 저장소가 가득 차면 해달은 쉬는 동작을 한다. 피로도 페널티로 오해할 문구는 쓰지 않는다.
- 애니메이션이 멈추거나 화면 밖에 있어도 생산 계산은 계속된다.

## 6. 낚시 시스템

### 6.1 역할과 조작

낚시는 결과를 열어보는 소소한 기대감을 담당한다. 반응 속도 미니게임은 없다. 최초 개방 후 “낚시 시작”을 한 번 누르면 자동 반복한다. 생산 주기가 완료될 때 물고기 1마리를 확정하고 내부 저장소에 넣는다.

- 기본 주기 120초, 최대 저장 10마리.
- 만석이면 중단, 수령 후 새 주기 시작.
- 도감 등록과 처음 발견 팝업은 플레이어 수령 시 발생한다.
- 실패, 미끼 소비, 장비 내구도는 없다.
- 결과는 완료 시 한 번 정해 저장한다. UI를 다시 열거나 앱을 재실행해 재추첨하지 않는다.

### 6.2 어종 데이터 — 초기 제안값

| ID | 이름 | 확률 | 개당 판매가 |
|---|---|---:|---:|
| fish_minnow | 피라미 | 45% | 10 |
| fish_carp | 붕어 | 30% | 15 |
| fish_perch | 농어 | 15% | 25 |
| fish_salmon | 연어 | 8% | 45 |
| fish_golden | 황금물고기 | 2% | 100 |

확률 합은 100%. 평균 판매 가치는 18.35조개/회, 시설 레벨 1의 이론상 시간당 기대 수익은 550.5조개다. 이는 장기 평균이며 특정 유저의 획득을 보장하지 않는다.

이번 버전에서는 모든 어종이 낚시 개방 시 추첨 대상이며 시설 레벨은 생산 시간만 줄인다. 희귀 어종 확률 증가, 천장, 지역별 어종은 구현하지 않는다. 황금물고기는 튜토리얼·마을 성장·필수 목표의 조건으로 삼지 않는다.

### 6.3 낚시 연출

대기/낚싯대 드리우기/찌 흔들림/물고기 들어 올리기를 짧은 루프로 표현한다. 완료 때마다 실제 전신 애니메이션을 모두 재생할 필요는 없다. 희귀 물고기를 최초 수령하면 물고기 카드와 해달의 기쁜 표정을 보여준다. 여러 신규 어종을 함께 수령하면 하나의 결과 패널에 묶는다.

## 7. 경제·강화·마을 성장

### 7.1 조개와 가방

- 재화는 조개 하나. 유료 재화는 없다.
- 가방은 itemId→수량으로 관리하며 이번 범위에서는 용량 제한이 없다.
- 수령할 때는 조개를 지급하지 않는다. 판매할 때만 현재 판매가×수량을 조개로 지급한다.
- 가방에는 품목별 수량·개당 가격·합계를 표시한다. MVP 판매 버튼은 ‘전체 판매’ 하나면 충분하다.
- 도감은 판매 이력과 별도로 영구 보존한다. 판매 전 확인 팝업은 생략한다.
- 생산·업그레이드·구매의 재화 연산은 정수 기반으로 한다. 음수 수량이나 잔액이 발생하는 요청은 거부한다.
- 입력 연타 방지뿐 아니라 명령 처리에서도 중복 구매·수령을 막는다.

### 7.2 시설 강화

농사와 낚시 레벨은 별개이며 각각 1~5다. 농사 레벨은 모든 밭에 적용한다.

| 현재→다음 | 농사 가격 | 낚시 가격 | 다음 레벨 시간 배율 |
|---|---:|---:|---:|
| 1→2 | 30 | 60 | 0.90 |
| 2→3 | 150 | 180 | 0.80 |
| 3→4 | 500 | 600 | 0.70 |
| 4→5 | 1,200 | 1,400 | 0.60 |

레벨 1 배율은 1.00. 각 레벨의 배율을 기본 시간에 직접 곱하며 누적 곱셈하지 않는다. `생산 시간 = ceil(기본 시간 × 해당 레벨 배율)`.

진행 중인 주기는 시작할 때 기록한 durationSeconds를 유지한다. 강화는 다음 주기부터 적용한다. 강화 팝업에는 “다음 생산부터 적용”을 표시한다. 레벨 5에서는 ‘최대 레벨’로 버튼을 비활성화한다.

### 7.3 마을 단계

| 단계 | 달성 조건 | 추가 가격 | 변화 |
|---|---|---:|---|
| 1 | 시작 | 없음 | 밭 1개와 잠긴 물가 표시 |
| 2 | 누적 판매액 500 이상 + 밭 2개 | 없음 | 호박, 밭 3 구매, 안내판 장식 구매 해금 |
| 3 | 누적 판매액 2,500 이상 + 농사·낚시 각각 레벨 3 | 없음 | 딸기, 벤치·꽃밭 장식 구매 해금 |

누적 판매액에는 목표 보상이나 개발자 지급을 포함하지 않는다. 단계는 조건 만족 시 자동 상승하며 조개를 차감하지 않는다. 여러 조건이 한꺼번에 충족되면 순서대로 처리하되 알림은 묶을 수 있다.

### 7.4 꾸미기

고정 위치 장식은 안내판 150, 벤치 400, 꽃밭 800조개로 제안한다. 구매 즉시 지정 위치에 나타나고 영구 유지된다. 생산 보너스는 없다. 구매 전 마을 미리보기를 보여준다. 장식 구매를 필수 목표에 넣지 않아 성장 강화를 늦추고 싶지 않은 유저도 진행할 수 있게 한다.

### 7.5 밸런스 검토 기준

첫 판매: 당근 5×2=10, 목표 보상 20을 합쳐 조개 30 → 농사 레벨 2 구매 가능 → 낚시 무료 개방. 이 경로에는 추가 대기나 재화 부족이 없어야 한다.

이후에는 플레이 방식에 따라 수익 차이가 커진다. 작물별 ‘저장소가 차는 시간’을 UI에 표시하고, 짧은 작물 때문에 오프라인 보상이 적어졌음을 이해할 수 있게 한다. 자주 접속하는 사람과 드물게 접속하는 사람의 성장 속도는 따로 관찰한다.

경제 검증 시 최소 세 시나리오를 계산한다: ① 30분 연속 플레이 ② 하루 3회, 회당 5분 ③ 하루 1회. 첫 강화, 밭 2, 마을 2·3 도달 시점과 잔액을 기록한다. 이 검증 전에는 3~7일 콘텐츠 분량을 확정하지 않는다.

## 8. 오프라인 생산과 시간 처리

### 8.1 기본 정책

- 앱이 백그라운드이거나 종료되어도 마지막 상태를 기준으로 생산 결과를 계산한다.
- 오프라인 계산 한도는 세션 간 최대 8시간. 시설 저장소 상한은 별도로 적용되며 먼저 도달하면 생산이 멈춘다.
- 예를 들어 기본 당근은 빈 저장소 기준 6분, 딸기는 60분, 낚시는 20분 후 가득 찬다. **8시간 내내 생산을 보장하는 구조가 아니다.**
- 짧은 저장 용량 때문에 재방문 가치가 부족하면 다음 실험에서 용량을 늘린다. 초기부터 별도 창고 성장 시스템을 만들지는 않는다.
- 수령되지 않은 완료 보상은 실제 경과 시간과 무관하게 소멸하지 않는다.

### 8.2 계산 규칙

1. UTC 기준 저장된 시각과 현재 시각의 차이를 구한다. 온라인 주기 경과는 단조 증가 시계를 활용해 일시적인 기기 시각 변경에 흔들리지 않게 한다.
2. 마지막 정산 이후의 유효 경과는 0~8시간으로 제한한다.
3. 진행 중이던 주기의 남은 시간을 먼저 소비한다.
4. 완료할 때 보상을 확정하고 내부 저장 회차를 증가시킨다. 전환 예약이 있으면 다음 작물에 적용한다.
5. 남은 경과 시간으로 다음 주기를 계산하되 저장 상한에서 즉시 멈춘다. 저장소가 가득 찬 뒤 지난 시간은 이월하지 않는다.
6. 상한에 닿지 않았다면 진행 중 주기의 잔여 시간을 보존한다.
7. 정산된 상태·추첨 진행 상태·정산 시각을 저장한 뒤 복귀 안내를 띄운다. 안내를 다시 열어도 보상이 추가되지 않는다.

최대 밭 3×6회+낚시 10회라 반복 계산 비용은 작다. 복잡한 대량 시뮬레이션 최적화는 필요 없다. 장시간 경과를 애니메이션으로 재생하지 않는다.

### 8.3 예외

- 시계가 과거로 이동하면 추가 생산을 지급하지 않고 로그를 남긴다. 미래였던 기준 시각을 무조건 현재로 낮춰 같은 구간을 중복 정산하지 않는다.
- 시계가 크게 앞당겨져도 한도와 저장 상한을 적용한다. 로컬 저장 방식은 완전한 시간 조작 방지를 제공하지 않는다.
- 복귀 시각을 조작한 후 원상복구하는 테스트를 포함한다. 온라인 플레이는 단조 시계로 계속 가능하게 하고 오프라인 기준 시각과 분리한다.
- pause/resume/focus 콜백이 연속 호출되어도 같은 경과 구간을 두 번 처리하지 않는다.
- 최초 실행은 오프라인 보상을 지급하지 않는다. 앱이 열려 있는 동안 정산한 시간을 종료 후 다시 지급하지 않는다.
- 복귀 패널은 ‘완료된 생산물’ 안내다. 패널 닫기는 수령이 아니다. ‘모두 받기’가 시설→가방 이동을 실행한다.

## 9. 화면 및 UI 명세

### 9.1 마을 메인 화면

상단에는 현재 조개, 마을 단계, 설정 버튼. 중앙은 해달·밭·낚시터를 가장 크게 보여준다. 하단에는 현재 목표 한 줄과 가방·도감·성장 버튼, 수령 가능한 보상이 있을 때만 활성화되는 ‘모두 받기’를 배치한다.

잠긴 시설도 실루엣으로 위치를 알려준다. 수령 가능 시설 위에는 아이콘과 개수, 생산 중에는 작은 진행 표시, 만석이면 ‘가득 참’을 표시한다. 상시 숫자와 배너로 해달을 가리지 않는다.

| 화면/패널 | 필수 표시 | 사용자 동작 |
|---|---|---|
| 농사 패널 | 작물, 다음 보상, 잔여 시간, 저장 회차, 전환 예약 | 작물 선택·예약 취소·수령 |
| 낚시 패널 | 잔여 시간, 저장 마릿수, 시설 레벨 | 최초 시작·수령 |
| 성장 패널 | 시설 레벨, 현재/다음 생산 시간, 가격, 해금 조건 | 강화·밭 개방·장식 구매 |
| 가방 | 품목, 수량, 단가, 판매 합계 | 전체 판매 |
| 도감 | 획득한 항목, 미발견 실루엣, 발견 수 | 항목 설명 열기 |
| 복귀 안내 | 부재 시간, 새 완료 수량, 만석 여부 | 모두 받기·닫기 |
| 설정 | BGM·효과음·진동, 버전 | 변경·닫기 |

### 9.2 UI 상태 규칙

- 패널은 하나씩 열고 Android 뒤로 가기는 최상단 패널부터 닫는다.
- 패널 위 터치는 마을 오브젝트로 전달하지 않는다.
- 조개 부족 버튼은 필요한 금액과 부족 상태를 표시한다.
- 빈 가방은 “아직 모은 생산물이 없어요”, 완료 보상 없음은 “해달들이 열심히 일하고 있어요”로 표시한다.
- 새로 발견한 도감 항목에 표시를 남기고 해당 항목을 확인하면 제거한다.
- 화면 비율에 따라 배경은 크롭할 수 있지만 버튼과 주요 시설은 Safe Area 안에서 유지한다. 이미지 종횡비를 유지한다.
- 작은 화면에서 긴 숫자와 한국어가 잘리지 않도록 레이아웃을 확인한다. 색상만으로 생산·만석 상태를 구분하지 않는다.
- 진동 기본값은 OFF. 긴 연출을 기다려야 다음 행동을 할 수 없도록 만들지 않는다.

## 10. 아트와 사운드

### 10.1 방향

따뜻하고 아늑한 해달 마을을 목표로 한다. 둥근 실루엣, 부드러운 자연색, 읽기 쉬운 시설 구분을 우선한다. 캐릭터 IP의 기준 얼굴·몸 비율·눈과 코 위치는 공통 기준 이미지로 고정한다.

이 문서에는 이전에 생성한 참고 이미지 원본이 첨부되어 있지 않다. 클로드에게 전달할 때 사용자가 선택한 해달 캐릭터와 인게임 참고 이미지를 함께 제공한다. 참고 이미지를 받기 전에는 임의의 새 캐릭터 디자인을 확정하지 않는다.

### 10.2 최소 에셋 목록

| 묶음 | 필요한 내용 |
|---|---|
| 배경 | 맵 1장 또는 최소 레이어 분리 배경 |
| 해달 | 공통 기본형, 농부 소품, 낚시 소품 |
| 동작 | 공통 대기·기쁨·쉬기, 농사 작업, 낚시 대기·낚아 올리기 |
| 농사 | 밭, 작물 3종×성장 3단계, 가방용 아이콘 3개 |
| 낚시 | 물가 시설·찌, 물고기 아이콘 5개 |
| 장식 | 안내판·벤치·꽃밭 각 1개 |
| UI | 조개·가방·도감·성장·설정 아이콘, 패널·버튼 공통 세트 |
| 효과 | 수확 반짝임, 코인/아이템 이동, 신규 발견 강조 |
| 소리 | 짧은 BGM 1개, 클릭·수확·판매·강화·발견 효과음 |

완성된 작업별 캐릭터를 모두 새로 그리기보다 기본형과 소품을 재사용한다. 아트 누락 시 플레이를 멈추지 않도록 임시 스프라이트를 사용한다. 외부 테스트 전에는 최소한 해달 기본형, 작업 동작, 수령 피드백을 갖춘다.

## 11. 기술 설계 가이드

### 11.1 책임 분리

| 구성 | 역할 |
|---|---|
| GameBootstrap | 데이터 로드, 세이브 로드, 오프라인 정산, 화면 연결 |
| ProductionService | 농사/낚시 주기와 저장 상한 처리 |
| InventoryService | 시설 보상 수령, 가방 수량 관리 |
| EconomyService | 판매·소비·잔액 검증 |
| ProgressionService | 시설 레벨·마을 단계·밭 개방·목표 처리 |
| CollectionService | 최초 획득과 도감 상태 |
| SaveService | 버전·검증·원자적 저장·백업 복구 |
| TimeProvider | 실제 시간과 테스트용 가짜 시간 공급 |
| AnalyticsSink | 테스트 이벤트 기록; 수집 방식 교체 가능 |
| View/Presenter | 화면 갱신과 명령 전달, 해달 연출 |

이름과 파일 분리는 예시이며 기존 구조에 맞게 조정한다. 모든 책임마다 인터페이스·싱글턴을 만들 필요는 없다. 시간과 이벤트 출력처럼 교체할 이유가 분명한 부분만 경계를 둔다.

### 11.2 데이터 구성

정적 데이터는 ScriptableObject 또는 프로젝트의 기존 데이터 방식을 사용한다. 플레이 세이브와 정적 설정을 혼용하지 않는다.

| 정의 데이터 | 최소 필드 |
|---|---|
| CropDefinition | id, displayNameKey, baseDurationSec, yieldCount, sellPrice, requiredVillageStage, spriteRefs |
| FishDefinition | id, displayNameKey, weight, sellPrice, spriteRef |
| UpgradeDefinition | facilityType, targetLevel, cost, durationMultiplier |
| PlotUnlockDefinition | plotId, cost, requiredVillageStage, requiredFarmLevel |
| DecorationDefinition | id, cost, requiredVillageStage, fixedAnchorId |
| GoalDefinition | id, conditionType, targetValue, rewardShells, unlockId |
| GameBalance | offlineCapSec, farmCapacityCycles, fishingCapacityCount |

ID는 표시 이름과 독립된 안정적인 문자열을 사용한다. 저장 후 이름을 바꾸더라도 연결이 깨지지 않아야 한다.

### 11.3 세이브 최소 필드

```text
schemaVersion, saveRevision, lastSettlementUtc
shells, lifetimeSales, villageStage
farmLevel, fishingLevel
plots[]:
  plotId, unlocked, activeCropId, queuedCropId
  state, cycleDurationSec, remainingSec
  storedCompletedCycles, storedItems{itemId: count}
fishing:
  unlocked, started, state, cycleDurationSec, remainingSec
  storedFishIds[], rngState
inventory{itemId: count}
discoveredItemIds[], ownedDecorationIds[]
goalProgress, claimedGoalIds[], tutorialFlags
settings, analyticsPendingEvents
```

실제 직렬화 방식에 따라 맵을 리스트로 변환할 수 있다. 선택한 JSON 직렬화기가 Dictionary를 지원하는지 확인한다. 정의 데이터의 UnityEngine.Object 참조를 세이브 JSON에 직접 넣지 않는다.

### 11.4 저장 정책

- 수령, 판매, 구매, 목표 보상, 작물 변경, 낚시 시작, 오프라인 정산 뒤 저장한다.
- 플레이 중에는 주기적 저장도 수행한다. 종료 콜백 한 곳에만 의존하지 않는다.
- 임시 파일 쓰기 → 유효성 확인 → 현재 파일 교체 → 백업 유지 순서를 사용한다.
- 한 저장 스냅샷 안에 잔액과 구매 결과, 가방과 시설 보상을 함께 기록해 한쪽만 저장되는 상황을 막는다.
- 손상 파일은 백업 복구를 먼저 시도하고, 실패하면 안내한다. 조용히 새 게임으로 덮어쓰지 않는다.
- 알 수 없는 아이템 ID가 등장해도 전체 로드를 실패시키지 않도록 명시적인 보존/제외 정책을 둔다. 마이그레이션 결과를 기록한다.
- 일반 설정을 제외한 핵심 진행 데이터를 PlayerPrefs 여러 키에 흩어 저장하지 않는다.

### 11.5 생산과 표시의 분리

생산 결과는 서비스가 결정하고 애니메이션은 상태를 표현한다. AnimationEvent가 보상을 직접 지급하지 않는다. 화면을 닫아도 생산과 목표 진행은 유지된다. 매 프레임 전체 오브젝트를 찾거나 전체 저장 파일을 쓰지 않는다. 생산 정산은 공통 시간 흐름으로 처리하고 UI 시간 표시는 필요한 빈도로 갱신한다.

### 11.6 개발용 도구

시간 진행, 조개 지급, 저장소 채우기, 세이브 초기화, 상태 확인을 개발 빌드 전용으로 제공한다. 일반 테스트 유저에게 실수로 노출하지 않는다. 개발자 지급 이벤트는 경제 및 성장 지표에서 제외한다. 초기화에는 확인 절차가 필요하다.

## 12. 분석과 피드백 계획

### 12.1 수집 방식

M1은 로컬 로그만으로 충분하다. 비공개 관찰 테스트는 로컬 이벤트를 파일로 내보내 분석할 수 있다. 원격 자동 수집이 필요해지는 단계에서 서비스·동의·보관 방식을 별도로 결정한다. 원격 수집이 없는 빌드에서 전체 유저 리텐션을 자동으로 알 수 있다고 가정하지 않는다.

개인 연락처나 자유 입력 원문을 생산 이벤트에 넣지 않는다. 테스트용 익명 설치 ID, 세션 ID, 빌드 버전, 이벤트 ID, UTC 시각을 공통 필드로 둔다. 재시도 시 같은 이벤트 ID로 중복을 제거한다.

### 12.2 필수 이벤트

| 이벤트 | 추가 데이터 | 목적 |
|---|---|---|
| session_start / session_end | sessionId, duration, endReason | 접속·체류; 강제 종료 시 end 누락 허용 |
| tutorial_step | stepId, status | 막히는 구간 |
| production_started | facilityId, itemId | 콘텐츠 진입 |
| reward_claimed | facilityId, items, offlineOrigin | 수령 빈도 |
| items_sold | quantities, totalValue | 경제 흐름 |
| upgrade_purchased | facilityType, fromLevel, toLevel, cost | 강화 선택 |
| plot_unlocked | plotId, cost | 확장 도달 |
| village_stage_reached | stage, elapsedPlaySeconds | 성장 속도 |
| collection_discovered | itemId | 수집 반응 |
| decoration_purchased | decorationId, cost | 외형 소비 |
| offline_settled | elapsedSec, simulatedSec, newRewards, capped | 방치 보상 체감 |
| save_recovery | reason, outcome | 데이터 안정성 |

생산 틱마다 이벤트를 전송하지 않는다. 온라인/오프라인 출처를 구분하려면 시설 저장 보상에 출처 집계도 함께 유지하거나 정산 이벤트를 별도로 분석한다. 구현하지 않은 필드는 추정값으로 채우지 않는다.

### 12.3 지표 정의

- 튜토리얼 완료율: 신규 정상 설치 중 목표 5까지 완료한 설치의 비율. 목표 8은 콘텐츠 완료율로 별도 계산한다.
- 첫 강화 전환율: 첫 세션 시작 설치 중 첫 강화 구매 설치의 비율.
- D1: 설치일의 다음 현지 날짜에 다시 접속한 설치 비율. 테스트 기준 날짜는 한국 시간으로 통일한다. D7은 설치 7일 후 같은 방식으로 계산한다.
- 리텐션 분모에는 관찰 기간이 지난 설치만 포함한다. 재설치·개발 빌드·내부 QA의 포함 여부를 기록한다.
- 세션 시간은 중앙값과 분포를 함께 본다. 백그라운드 시간을 적극적 플레이 시간에 포함하지 않는다.
- ‘농사만/낚시만/둘 다’ 이용 비중과 시설별 만석 시간을 확인한다.

### 12.4 테스트 순서와 판단

**1차 관찰 테스트: 5~10명.** 첫 10분은 설명 없이 플레이하도록 하고 어디서 멈추는지 기록한다. 숫자로 시장성을 판정하지 않는다. 게임을 좋아할 법한 사람과 그렇지 않은 사람을 구분해 피드백을 읽는다.

**2차 비공개 테스트: 30~50명, 약 7일.** 초반 이해도, 다음 날 접속 이유, 콘텐츠 소진 시점과 버그를 확인한다. 가능하면 지인 외 참가자도 포함한다. 이는 방향 탐색 규모이며 성공을 통계적으로 확정하는 표본이 아니다.

테스트 직후 물을 질문:
1. 무엇을 하면 마을이 발전한다고 이해했는가?
2. 가장 좋았던 순간과 가장 귀찮았던 순간은 무엇인가?
3. 다시 접속했다면 무엇을 기대했는가? 안 했다면 무엇이 부족했는가?
4. 농사와 낚시 중 어느 쪽을 더 보고 싶었고 그 이유는 무엇인가?
5. 다음에 하나만 추가된다면 무엇을 원하는가? 먼저 자유 답변을 받고 선택지를 제시한다.

아래 수치는 **팀 내부의 임시 점검선**이며 장르 벤치마크가 아니다.

| 관찰 | 다음 행동 |
|---|---|
| 튜토리얼 완료율 80% 미만 | 기능 추가보다 초반 안내·시간·버튼 수정 |
| D1 30% 이상 + 자발적 복귀 이유가 반복적으로 확인 | 다음 소규모 콘텐츠 실험 검토 |
| D1 15~30% 또는 표본/수집 불완전 | 원인 한 가지 수정 후 재테스트 |
| D1 15% 미만이 두 번의 수정 후에도 지속 | 확장 중단·핵심 루프 변경 검토 |
| 캐릭터 반응은 좋고 플레이 복귀는 낮음 | IP 매력과 게임 루프 문제를 분리하여 판단 |
| 콘텐츠를 다 본 사람이 계속 돌아옴 | 작물/물고기/장식 중 요구가 분명한 것부터 추가 |

리텐션 숫자 하나로 자동 종료하지 않는다. 설치 출처, 기기 문제, 콘텐츠 소진, 보상 부족, 목표 이해 실패를 함께 확인한다. 유료 광고 집행이나 대규모 콘텐츠 생산은 이번 실험 결과만으로 결정하지 않는다.

## 13. 개발 단계와 완료 조건

1인 개발 기준의 **작업량 추정**이다. 아트 제작 상태와 기존 코드 품질에 따라 달라지며 출시 약속이 아니다. 아래 개발 20작업일 뒤 비공개 관찰 기간 약 7일을 별도로 둔다.

| 단계 | 예상 | 범위 | 완료 조건 |
|---|---:|---|---|
| M0 준비 | 1일 | 프로젝트 확인, 데이터·화면 뼈대, 범위 고정 | 현재 버전에서 실행, 필요한 자산·의존성 목록 확인 |
| M1 농사 수직 슬라이스 | 3일 | 밭 1·당근·수령·가방·판매·농사 첫 강화·기본 저장 | 처음부터 강화까지 진행, 재실행 상태 보존 |
| M2 농사·낚시 반복 | 4일 | 밭 3·작물 3·낚시·어종 5·강화·만석 | 모든 생산·전환·수령 흐름 정상 |
| M3 시간·성장 안정화 | 4일 | 오프라인 정산, 백업, 마을 단계, 목표·도감 | 중복 지급 없이 종료·복귀·시간 예외 처리 |
| M4 감성·사용성 | 4일 | 해달 동작, 장식, UI·사운드·초반 안내 | 설명 없이 첫 루프 이해, 세로 비율 대응 |
| M5 테스트 준비 | 4일 | 이벤트, 경제 점검, 기기 검증, 치명 버그 수정 | 설치 가능한 테스트 빌드·관찰 시트 준비 |

M1에서 재미가 전혀 보이지 않으면 아트 피드백을 붙여 짧게 재평가한다. M5까지 무조건 구현을 밀어붙이는 계약처럼 운영하지 않는다. 일정이 늘어지면 장식 수량과 부가 연출부터 줄이되 저장 안정성과 첫 플레이 흐름은 유지한다.

## 15. 확장 결정 이후의 후보

아래는 백로그일 뿐 MVP 요구사항이 아니다. 한 번에 한 가지 가설만 검증한다.

| 발견한 반응 | 가장 작은 다음 실험 |
|---|---|
| 농사가 좋지만 작물 선택 의미가 약함 | 생산 시간대가 다른 작물 1종 추가 |
| 낚시 수집 요구가 강함 | 어종 2~3종 또는 도감 연출 확장 |
| 해달 동작 자체를 오래 봄 | 반응 동작 2개·소품 1개 추가 |
| 성장해도 마을이 비슷하다는 의견 | 단계별 배경/시설 외형 변화 확대 |
| 장기 부재 보상이 너무 적음 | 저장소 상한만 변경한 버전 비교 |
| 수령·판매가 번거로움 | 일괄 동선 단축 또는 자동 판매 실험 |
| 자발적 재방문·꾸미기 수요가 확인됨 | 소규모 장식 묶음과 수익화 설계 검토 |

요리 콘텐츠는 이번 게임의 자연스러운 다음 단계로 자동 편입하지 않는다. ‘해달 식당’과의 역할 분리가 유지되는지 별도 판단한다. 수익화도 잔존율 확인 후 정하며, 광고 없이도 성장이 가능한 경제를 우선 유지한다.

## 16. 클로드의 첫 응답과 첫 납품 형식

첫 응답에는 다음만 담는다.

1. 프로젝트를 확인할 수 있는지와 실제 확인한 엔진·구조.
2. 문서와 충돌하는 기존 구현 또는 구현을 막는 정보.
3. M1에서 만들 파일·데이터·화면의 짧은 목록.
4. 작업 환경이 있다면 M1 구현 착수. 없다면 M1 스크립트와 연결 절차 제공.

M1 납품에는 다음을 포함한다.

- 밭 1개에서 당근을 생산하고 수령·판매·첫 강화까지 가능한 코드.
- 재실행 시 조개·가방·밭 진행·시설 레벨이 보존되는 기본 저장.
- 필요한 GameObject/컴포넌트/Inspector 필드 연결 절차.
- 첫 판매 후 조개 30 확보와 첫 강화 구매가 가능한지 확인 결과.
- 확인하지 못한 내용과 다음 단계에서 해결할 항목.

**개발의 성공 기준은 기능 목록을 많이 채우는 것이 아니다. 적은 콘텐츠로도 해달을 보고 싶고, 생산물을 받으러 다시 들어오고 싶은지 판단할 수 있는 버전을 만드는 것이다.**
